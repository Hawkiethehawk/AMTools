# AMDC 项目规则

## 版本与发布

- 版本号只在准备推送到 Gitee 时处理；本地修改或未推送提交不得自动递增版本号。
- 只有应用代码、项目配置、依赖或运行逻辑发生变更时，推送才视为一次版本发布。
- README、截图、说明文档和协作规则等纯文档变更沿用当前版本，不增加版本号、不新增版本发布记录，也不创建新版本标签。
- 对属于版本发布的推送，默认拟在当前版本上增加 `0.0.1`；用户指定版本号时使用指定版本号。执行版本文件更新、`CHANGELOG.md` 记录、创建标签或推送前，必须先向用户报告当前版本和拟发布版本，等待明确确认后才能执行。
- 用户明确要求不修正版本号时保持当前版本，并按该要求推送；未获版本确认时不得修改版本、创建标签或推送。
- 版本发布前同步更新 `package.json`、`package-lock.json` 和 `CHANGELOG.md`。
- `CHANGELOG.md` 必须记录版本号、发布日期和实际变更，并写明本次发布的验证结果。
- 版本发布提交完成后创建同版本的 `vX.Y.Z` Git 标签，再将提交和标签推送到远程仓库。
- 每次更新 Gitee 版本后，必须把同一版本号同步到 AMDC README；如本机私有配置绑定了项目介绍文档，再按授权同步并回读确认。
- 如果待发布内容包含应用代码、项目配置、依赖或运行逻辑变更，必须先向用户列出功能变更、影响范围和验证结果，获得用户明确确认后才能纳入版本、CHANGELOG、提交、标签和推送；未获确认时只能处理纯文档同步，不能发布功能改动。

## 页面控件

- 新增下拉选项时，默认复用看板现有 Top 100/Top 1000 的 `sort-menu`、`sort-trigger`、`sort-options` 组件和交互，不单独使用另一套样式。
- 页面内所有弹框、弹窗、确认提示、错误提示、下拉栏、日期日历及同类交互控件必须使用浏览器或平台原生控件，不得仿制原生外观或另建自定义替代组件。
- 调试和验证默认使用无头浏览器；服务重启必须设置 `AMDC_NO_OPEN=1`，不得自动打开可见浏览器窗口。

## 采集核心机制

- 多周任务默认按采集周串行执行，顺序为最新周到最旧周；完成当前周后才能启动下一周。
- 每个采集周由全部已选账号共同处理该周全部品类的国别应用队列，不得改成一个账号负责一个采集周。
- 账号分工、采集周顺序、任务并行方式和总进度口径属于受保护的核心机制。任何调整必须先向用户说明具体方案、影响和取舍，并取得明确确认后才能修改代码。
- 用户要求“给出方案”或讨论可行性不等于授权实施，不得据此改变现有采集机制。

## 运行与验证安全

- 修改看板后需要重启服务时，先检查采集任务和飞书批量同步任务是否正在运行；存在运行中任务时，未经用户明确允许不得重启。
- 默认使用语法检查、契约测试、健康检查和只读 API 验证修改，不因排障或验证擅自启动真实采集。
- 真实采集、真实飞书同步以及其他会消耗账号额度或改变外部数据的操作，必须有用户明确授权；账号处于限流状态时尤其不得自行发起新任务。
- 用户要求停止任务后，不得自动恢复、续跑或新建采集任务，除非用户再次明确要求。

## 飞书同步边界

- 与飞书同步规则无关的修改，不触发飞书同步。
- 修改飞书同步规则后，只有用户明确要求实施同步时才执行真实同步；否则仅做本地或隔离验证。
- 批量同步期间必须锁定相关同步入口，并以全部选中记录为整体计算和展示进度，不能按单个采集周反复归零或提前显示完成。

## 实施反馈

- 交付反馈只陈述实际完成并验证过的工作，明确区分已验证、推断和未测试内容。
- 未执行飞书同步时，不主动写同步相关内容，更不得表述为“已同步”。
- 未推送远程仓库时，不得表述为“已推送”；未完成端到端验证时，不得仅凭语法通过或服务启动就表述为“已完成验证”。

## 数据与文档产出

- 用户提到“AMDC 数据”时，默认指 AMDC 飞书电子表格中的数据；只有用户明确指定本地文件时，才改用本地 Excel 或其他数据源。
- 所有新建的飞书云文档默认保存到用户的“我的文档库”（创建时使用 `--parent-position my_library`）；用户明确指定其他目录或知识库时，以用户指定位置为准。
- 项目介绍、数据表格和市场分析文档的地址只保存在本机私有配置中，不写入仓库、日志或反馈。
